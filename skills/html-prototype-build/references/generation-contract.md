# Single-Page HTML Prototype Generation Contract

## Delivery loop

The following three items are the only mandatory paths in this file; the remaining sections only explain details:

1. Select the minimal UI pack dependency closure from the manifest.
2. All business state is submitted only through `PrototypeViewers`; the UI pack Adapter only renders local state.
3. Before delivery, verify item by item against the [delivery review checklist](delivery-checklist.md).

## 1. Scope & precedence

This contract governs all single-page HTML product prototypes subsequently generated by AI. Each deliverable uses a standalone parent directory; inside, only the page entry HTML, handoff notes, and supporting files organized by responsibility are kept. When conflicts arise, execute in this order:

1. The user's explicit requirements in the current task.
2. The `design-system.md`, foundation contract, and base source files of the currently selected UI foundation.
3. The manifest, component contract, and component implementation of the currently selected UI provider.
4. The composition constraints in `ui/contract.md` and the corresponding `PACK.md`.
5. The annotation contract in `addons/annotations/`, and the formal Client Runtime behavior of `runtime/client/core/`, `runtime/client/notes/model.js`, and `runtime/client/notes/viewer.js`.

This file only keeps the hard constraints shared by every generation path. The operational steps for UI generation, product annotations, the local authoring service, review pinning, screenshots, and delivery are governed by the corresponding entry documents in this same directory.

## 2. Visuals

- Define and use Tokens in `prototype/prototype.css` consistent with the current foundation's `design-system.md` and `foundation/tokens.css`.
- Foundation and project materials must use named tokens; layout dimensions may stay in the page CSS as long as they come from the current materials.
- If a requirement adds visual values without sufficient evidence, do not invent tokens; omit the visual or use `ponytail:` to mark the current ceiling and the evidence required to upgrade.
- Tailwind, if used, may only handle layout, e.g. flex/grid, positioning, width/height, overflow, and responsive visibility; it must not use Tailwind color, border, radius, shadow, font, font-size, line-height, spacing, or interaction-state classes to override `ui-*` visual tokens.

## 3. State & scenarios

- Every prototype generates `prototype/notes.snapshot.js`, which is both the single annotation data source and the scenario state source for `PrototypeViewers`; generating a duplicate `notes.json` or writing the same card data into the HTML is forbidden.
- The data file must assign the object to `window.__PROTOTYPE_NOTES__` and include `schemaVersion: 2`, a complete base `state`, `activeScenario`, `scenarios`, `header`, and `cards`.
- `scenarios` is an object keyed by stable scenario ids; each scenario's standard structure is `{ extends?, state }`. `state` expresses composable business state such as page, overlay, tab, and data states; when reusing a base scenario through `extends`, only the differences are kept.
- `PrototypeViewers` is provided by `runtime/client/core/state.js` and is the single source of state; submit state only through `registerState` / `setState` / `patchState` / `activateScenario`.
- The UI pack's `state-adapter.js` only provides `normalize` / `render` projections of component-local state; the prototype's business Adapter is responsible for calling it, and the UI pack must not hold business state directly or subscribe to `PrototypeViewers`.
- Do not infer business state from DOM classes, ARIA, or state-specific `data-*` attributes, and do not add attribute protocols for page, overlay, tab, or data states.
- Cards match against the normalized complete state with `when` using AND logic; the matching implementation is uniformly provided by `runtime/client/notes/model.js`. The primary format is flat dot-paths, e.g. `{ "product.page": "list", "product.layers.includes": "create", "product.tabs.modal": "rules" }`; simple equality also supports nested objects. List-state cards must also constrain `product.layers` to an empty array, so list annotations do not still show while a modal is open.
- Cards without `when` always display.
- `header` always displays; the right rail shows only connected annotation cards.

## 4. URL scenarios

Notes Viewer handles restoration of `?scene=<id>` and `?collapsed=1`; `runtime/client/core/state.js` only handles state, scenario registration, and activation, and does not parse the URL itself. The business Adapter does not parse the URL either; it only consumes the unified state. New deliverables generate only `scene` links.

Screenshot operations and acceptance follow [screenshots.md](screenshots.md).

## 5. Annotations

The number of annotation points is decided by the requirements, with no fixed ceiling:

- Any point that needs interaction description or logic explanation should get an annotation and a connector; controls that need no explanation are not annotated.
- One annotation corresponds to one semantic unit: controls that jointly accomplish one thing are merged into a region annotation, e.g. "Reset + Search" become the search region, and a table together with its pagination is one unit — do not split by DOM node.
- Do not connect every control just to pad coverage or seek completeness, and do not skip points that genuinely need explanation out of fear of quantity.
- Prefer reusing a stable, unique `id` for the prototype target element; cards save the id without `#` in `target.anchor`, and may carry `target.label` for humans and AI. Only when an element is genuinely unsuited for an id do you add `data-prototype-note-target`, binding compatibly via `target.selector`.
- Nodes that already have an `id` must not get a duplicate `data-prototype-note-target`; annotation anchors express identity only and do not store business state.
- The Viewer creates the right rail, connectors, numbers, and mobile rendering; the main HTML must not hard-code these.

Interaction marks and annotation points are orthogonal:

- `data-ui-interactive` marks only the entry points requiring user action in this iteration's business, shown as a coral lightning symbol at the element's inner top-right corner.
- The source of judgment is the operations newly added or changed in the current requirements, not every clickable control on the page.
- Repeated operations of the same kind are marked once; per-row edit/delete in a table is marked on a representative row only.
- Do not mark shell branding and top navigation, sidebar collapse, close, cancel, pagination jumps, or existing controls unrelated to this iteration's requirements.
- Interaction marks carry no explanatory text, take no annotation cards, and do not participate in connector drawing; the same element may be both a `target.anchor` and carry `data-ui-interactive`.

## 6. Overlays

- The Modal overlay covers only the left product area and must not cover the right annotation area.
- `.ui-overlay` must be a positioned child inside `.ui-preview` or use an equivalent product-area boundary; a global `fixed inset: 0` covering the whole viewport is forbidden.
- When a Modal opens, submit the overlay state to `PrototypeViewers`, connecting only annotations whose `when` matches and whose target is visible; restore the previous composed state on close.
- A Drawer used as product interaction must also stay within the left product area and not cover the right annotations.
- Modal / Drawer must give the inner panel `.ui-modal` / `.ui-drawer` a stable `id`; `target.anchor` binds the inner panel id. The overlay layer's `.ui-overlay` `id` must not be used as an annotation connector anchor.

## 7. Delivery files

Every prototype generates the same structure:

```text
<prototype-name>/
├─ AGENTS.md
├─ prototype.html
├─ prototype/
│  ├─ prototype.css
│  ├─ prototype.js
│  ├─ notes.snapshot.js
│  ├─ display-mode.js
│  ├─ state.js
│  ├─ model.js
│  └─ viewer.js
├─ screenshots/
└─ assets/
```

- `<prototype-name>/` is a complete, independently handoff-able final product directory; its name comes from the current task and is stable and filesystem-safe.
- Copy `templates/AGENTS.md` verbatim to `<prototype-name>/AGENTS.md`. It requires downstream coding agents to extract product information only from the snapshot, screenshots, and anchor-scoped HTML locals, and not to port the prototype implementation into the target project.
- `<prototype-name>/` may contain only `AGENTS.md`, `prototype.html`, `prototype/`, `screenshots/`, and an `assets/` created on demand; do not scatter CSS, JS, snapshot, or runtime files.
- The HTML loads `./prototype/prototype.css` in `<head>` and, before `</body>`, loads `./prototype/notes.snapshot.js`, `./prototype/display-mode.js`, `./prototype/state.js`, `./prototype/model.js`, `./prototype/viewer.js`, and `./prototype/prototype.js` in order. Paths must be relative to the HTML so the page can be opened directly under `file://`.
- `prototype.html` keeps a readable page DOM, stable anchors, and minimal asset references; inlining large CSS blocks or business scripts is forbidden.
- The formal Client Runtime uses four verbatim copies: `prototype/display-mode.js` copied from `runtime/client/core/display-mode.js`, `prototype/state.js` from `runtime/client/core/state.js`, `prototype/model.js` from `runtime/client/notes/model.js`, and `prototype/viewer.js` from `runtime/client/notes/viewer.js`; the four must not be re-merged into a single Viewer file.
- `display-mode.js` handles `product-only` and overlay decisions, `state.js` only coordinates `PrototypeViewers` state, `model.js` only handles scenario metadata and pure `when` matching, and `viewer.js` only handles Notes Viewer DOM and connectors; the four responsibilities must not feed back into each other.
- When a chart component depending on `data._echarts-core` is selected, copy `vendor/echarts/echarts.min.js` to `assets/echarts.min.js`, and copy `runtime/client/charts/bridge.js` and `runtime/client/charts/presets.js` into `prototype/`; load ECharts and the chart runtime before `notes.snapshot.js`.
- When `data.chart-map` is selected, also copy the corresponding geo json/js to `assets/maps/`; under `file://`, fetching JSON is blocked, so the geo must be pre-registered into `window.PrototypeMapRegistry` by a script. Map geo must not reference a CDN or be written into `component.html`.
- Screenshots are stored only under the root `screenshots/` and are not a page runtime dependency; `assets/` must not be an empty directory.
- `runtime/author/`, `runtime/server/`, and `runtime/cli/` are not formal page runtime dependencies; Author Bootstrap, Direct edit, Notes editor, Inspector, the local service, and source-locating information must not enter the formal deliverable.
- Direct edit is loaded dynamically only in the authoring service session; style and copy changes are written back to the source HTML via `/__prototype-author/edit` and do not enter the formal HTML load structure.
- Mark is loaded dynamically only in the authoring service session; pins write only to localStorage and never inject any runtime into the source HTML, so the formal delivery needs no "strip Mark injection" step.
- Forbid inlining any annotation editing logic in `prototype.html` (including `file://`-specific scripts, `prompt()`-based note edits, or writing card overrides/custom notes to localStorage); `file://` only displays the snapshot read-only, and editing must go through `runtime/server/index.mjs` as described in [local-authoring.md](local-authoring.md).

## 8. Dependencies

- default to native HTML, CSS, and JavaScript, with no external CDN dependency.
- External CDNs may be introduced only when the user explicitly asks, or when the prototype goal cannot be reasonably achieved with existing local resources and platform-native capabilities.
- confirm necessity before introducing anything; do not pull in Tailwind, Font Awesome, React, or external component library resources for icons, layout, basic components, or light interactions.
- Prefer text symbols, inline SVG, or existing legal local resources for icons, and provide an accessible name.

## 9. content & data

- Forbid carrying any example business names, system names, menu names, field names, codes, people, departments, channels, dates, or data over from historical prototypes or other tasks.
- Forbid mistaking structural examples in components, Patterns, or Presets for the user's business content; after copying, replace them with the current requirements or neutral placeholders.
- Do not use real login credentials, tokens, API addresses, personal information, production data, or unauthorized brand assets.
- Local mocks express only the minimal data relationships needed by the current interaction and must not expand business rules the user did not ask for.
- When the user's information is insufficient to determine business meaning, stay neutral and explicitly mark as pending confirmation; do not "fill in to look more like a real system".

## 10. Accessibility

- Use appropriate semantic elements such as `header`, `nav`, `main`, `aside`, `section`, and `article`.
- Every icon-only button must provide a clear `aria-label`.
- Tabs must maintain `role="tablist"`, `role="tab"`, `role="tabpanel"`, `aria-selected`, `aria-controls`, and `aria-labelledby`.
- Dialogs must maintain `role="dialog"`, `aria-modal="true"`, and an associated title.
- Custom Selects must maintain `aria-haspopup="listbox"`, `aria-expanded`, `role="listbox"`, `role="option"`, and `aria-selected`.
- If a tree uses `role="tree"` / `treeitem`, it must at least maintain `aria-expanded`; if the required keyboard behavior is not implemented, mark it explicitly with `ponytail:` as a static or limited-interaction demo only.
- Keyboard focus must not rely only on low-contrast borders; when no formal focus visuals have been captured, keep the browser's visible focus and annotate it with `ponytail:`.
- Do not declare contrast-deficient combinations already flagged by the design system as passing accessibility acceptance.
